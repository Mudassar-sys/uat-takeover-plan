01 / The role

The role, as we read it

Four outcomes. Your engineers keep the build; this role owns requirements, testing and coordination.

1

Requirements baseline

Discovery recordings turned into one requirements matrix: each requirement, what was built for it, the UAT script that tests it, and its status. Open items closed with stakeholders and engineers and signed off in writing.

2

UAT from start to finish

Plan, scripts by role, entry and exit criteria, defect severity rules, daily triage, two test cycles and a written go/no-go.

3

The website side

Every .NET/AWS flow that writes to Salesforce mapped, tested end to end with the website team, and its authentication checked.

4

Engagement ownership

Weekly status, risk log and change control, then cutover, go-live, hypercare and steady-state support.

Salesforce describes the functional consultant as the person who leads and supports the customer through the implementation lifecycle, including analysis, design and development R1. Its Business Analyst certification covers discovery, stakeholder collaboration, process mapping, requirements, user stories and user acceptance R2.

02 / How we work

How we work

  • 25 hours a week committed to the role, up to 30 in the heavy UAT weeks.

  • Every week starts with named deliverables and dates, agreed in writing.

  • Each week is its own milestone. You review that week's deliverables and approve before it's paid.

    Milestones are funded in escrow before work begins. When a week is submitted, you have 14 days to review it and either approve it or request changes U1.

  • Our CEO is your point of contact. If you'd rather work day to day with the consultant, we set up one shared group with you, the consultant, our team and our CEO, so there is always a check on quality. Meetings and triage run in US Eastern hours, with a short written update every day.

From the discovery recordings to hypercare, with a written sign-off before anything reaches production.

1

A validated deployment can be quick-deployed within 10 days without re-running Apex tests S16S17.

3

05 / Integration checkpoints

Integration checkpoints

We don't assume how your website talks to Salesforce. These are the checkpoints we verify in integration testing.

  1. Secrets stay out of code: AWS Secrets Manager stores and rotates OAuth tokens and API keys, so credentials are not hard-coded in source A1.
  2. New integrations use External Client Apps: since Spring '26, creating new connected apps is disabled by default, and existing ones keep working S7S8.
  3. No username-password logins: Salesforce is deprecating that OAuth flow and recommends migrating to more secure flows such as client credentials S9.
  4. A dedicated API-only integration user: Enterprise, Unlimited and Performance orgs include five Salesforce Integration user licenses S10.
  5. No duplicates on retry: writes upsert on an External ID, so a matched record is updated instead of created again S12.
  6. Failures are inspectable: messages that are not processed successfully move to an SQS dead-letter queue A2.
  7. API budget checked: Enterprise Edition gets 100,000 API calls per 24 hours plus 1,000 per Salesforce license S11.
  8. Form caps known: Web-to-Case captures up to 5,000 cases per 24 hours S6.
  9. Events only if needed: Event Relay forwards custom platform events and Change Data Capture events to Amazon EventBridge S13S14.
  10. Test data handled: masking sandbox data with Data Mask & Seed needs the Salesforce Data Mask add-on license S19.
06 / Day one

Two platform changes to check on day one

Salesforce is deprecating the OAuth username-password flow, and since Spring '26 new connected apps are disabled by default, so new integrations go through External Client Apps. If a backend still logs in with a username and password, moving it to client credentials or JWT belongs in the UAT plan, not after launch. S7S8S9

09 / The team

The team behind the role

Salesforce consultants, admins, developers and architects, holding between 5 and 12 Salesforce certifications each, plus .NET and AWS engineers for the website side. You choose from three consultant profiles before we start, our CEO stays your point of contact, and the work doesn't stall when someone is out.

10 / Scope

Scope boundaries

In scope

  • The four outcomes above: requirements baseline, UAT from start to finish, the website side, and engagement ownership

Not in scope unless agreed

  • Build changes in Salesforce (your engineers)
  • .NET code changes (the website team)
  • License purchases
  • Running a data migration
11 / What we need

What we need from you, in writing

  • Discovery recordings
  • Sandbox access and read-only production access
  • Access to your defect tool (Trello or Asana)
  • A contact on the website team
  • The current open-items list
  • The target go-live date
  • The number of business testers
12 / Questions

Four questions to lock Week 1

  1. Is the org on NPSP or Agentforce Nonprofit (formerly Nonprofit Cloud), and is Service Cloud in scope?
  2. Which sandbox is UAT running in, and is the test data masked?
  3. Which website flows write to Salesforce, and how does the .NET backend authenticate today?
  4. What is the target go-live date, and how many business testers will you have?

Agentforce Nonprofit is the current name of Nonprofit Cloud N1.
